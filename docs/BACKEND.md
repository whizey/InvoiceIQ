# Backend

FastAPI app in `backend/app`. Endpoints are listed in [API_REFERENCE.md](API_REFERENCE.md); this page is about how the
pieces fit.

## Accounts, workspaces and sessions

All of this is in `app/api/portal.py`.

Registering creates a user, a company workspace and an `owner` membership in one go. Passwords (12 to 256 characters)
are hashed with scrypt and a random 16-byte salt and compared in constant time. A session token starts with `iqp_`;
only its SHA-256 digest is stored, and sessions last 8 hours. Five wrong passwords lock the account for 30 seconds,
doubling up to 15 minutes, and an unknown email is treated exactly like a wrong password so accounts can't be probed
(`app/core/login_throttle.py`).

Roles are `owner`, `admin` and `reviewer`. Importing needs owner or admin, decisions, notes and reminders need
reviewer or above, and deleting the workspace's data needs the owner.

There are two public workspaces, both `kind="showcase"`. Visitors get a session without an account, and anything they
write (decisions, notes, reminders) is tagged with their session, so each visitor only sees their own on top of the
shared history.

- Kaveri Industrial Supplies (`SHOWCASE_ID`) is generated by `app/seed/showcase_seed.py` relative to today and
  rebuilt when it goes stale. It's loaded through the same importer customers use, from a generated Zoho Books export.
- The real 2015 ledger (`PUBLIC_LEDGER_ID`) is loaded by `scripts/provision_public_ledger.py` from the public dataset
  (downloaded and checksum-checked on first start). Its workspace has `as_of = 2015-11-30`.

A workspace with `as_of` set lives on that date. Portal code must use `workspace.today()` and `workspace.now()`
rather than `date.today()`, so overdue counts, forecasts, reminder rules and the assistant all agree on what "today"
means.

Every query is filtered by the caller's `workspace_id`, which comes from the `identity` dependency, and there are
tests that try to read and write across workspaces.

## Getting data in

`POST /portal/import-preview` and `/portal/import-file` take a Zoho Books invoice export or Tally's Bills Receivable
report, CSV or Excel, up to 2,000 invoices (`app/services/ledger_import.py`). The importer finds the header row
(Tally puts a title block above it), maps columns by name, reads Indian date formats and "Dr/Cr" amounts, and
reports skipped rows by reason with their row numbers. The preview never writes anything, so public-workspace
visitors can try it with their own file. Importing scores the workspace straight away.

The older `POST /portal/import` (a fixed CSV layout, 250 rows) is still there for the tests and scripts that use it.

## Follow-ups, scores and the forecast

`GET /portal/follow-ups` returns the ranked list, the cash forecast and the model comparison in one response
(shared by all visitors of a workspace through the read cache).

- `services/follow_up.py` ranks overdue invoices by balance × chance of paying late × days overdue. The chance is a
  per-customer baseline (late share over the last six settled invoices, smoothed toward the workspace's rate)
  unless the model beats it by 0.02 AUC on the workspace's invoices due in the last six months. It also builds the
  calibration table and flags when the workspace's invoices are ones the model was trained on.
- `services/late_reasons.py` picks the one-line reason: dispute, part payment, what the customer said or promised,
  usual lateness, then the latest note. Notes flagged as prompt-injection attempts are never quoted.
- `services/cash_forecast.py` fits a Kaplan-Meier curve of days from due date to payment, per risk band, and
  works out each open invoice's chance of being paid in each coming week given its age. It re-runs itself as of each
  of the last six four-week periods and widens the range to cover how far off it was.

Model scores come from `services/portal_risk.py`, which builds posting-time features (nothing known after the
posting date) and scores every invoice with the verified LightGBM model.

## Reminders

`services/reminders.py` and three endpoints. `POST /portal/reminder-draft` checks the rules first: no reminder on a
disputed invoice, none within three days of the last, and a flag for a manager when the balance is ₹5 lakh or more or
the invoice is over 60 days late. Then the model drafts from the invoice's facts only. A draft is thrown away if it
contains a number that isn't in those facts, if it was cut off, or if it doesn't name the invoice; after that the next
model is tried, then a template. `POST /portal/reminders` records one the person has sent (and checks the rules
again). `GET /portal/reminders` lists them with the first payment that followed within 14 days.

## Decisions, notes and alerts

Recording a decision (`APPROVE`, `REJECT`, `ESCALATE`, `RESET`) writes the decision and an event in the same
transaction; the event raises or closes an approval alert ([EVENT_PIPELINE.md](EVENT_PIPELINE.md)). An invoice's
status is its latest decision. Notes are free text on an invoice; they're embedded for search when a Gemini key is
set.

## Reads and caching

Read endpoints use a short per-workspace cache that every write invalidates. Results that are the same for every
visitor (the invoice rows, follow-ups, the dashboard) are shared; anything that depends on a visitor's own decisions is
cached per session. Lists are filtered and paged in memory from the cached rows.

## Deleting data

`POST /portal/erase` (owner only, confirmed with the company name) deletes the workspace's invoices, payments,
notes, decisions and reminders, and also the copies held in outbox and dead-letter payloads, alerts, risk rows and
assistant traces. With `scope=account` and the password it deletes the workspace and the user too.

## The older recovery workflow

Before the portal there was a single-company recovery API (`/companies`, `/invoices`, `/recovery-cases`) driven by a
LangGraph workflow in `app/agents/graph.py`: load context, score risk, have the model diagnose and propose an action,
run it past the policy engine, and execute only if allowed. It's still in the codebase and tested, but a guard
middleware blocks those routes on the public deployment, and the product no longer leads with it.

The policy engine (`services/policy_engine.py`) is plain Python with fixed thresholds, checked in this order: a broken
promise to pay escalates; ₹10 lakh or more and 45+ days overdue escalates; an escalated case gets no automatic
reminders; after three reminders it escalates; reminders are at least seven days apart; a high-value reminder waits
for a person (`services/review_gate.py`); otherwise the reminder goes ahead.
